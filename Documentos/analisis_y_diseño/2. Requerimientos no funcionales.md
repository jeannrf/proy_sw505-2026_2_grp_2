## 1. Restricciones, supuestos e interfaces

### 1.1 Restricciones

| Tipo | Restricción |
|---|---|
| Arquitectura | 7 capas: presentación, redirección y seguridad, negocios, integración, acceso a datos, gestión documental, y observabilidad y auditoría |
| Datos | Base relacional + base documental (NoSQL) + almacenamiento de objetos |
| Despliegue | Docker Compose; solo Nginx expone puertos |
| Calidad | CI con lint, tipos, pruebas y cobertura de ramas ≥ 70 % en la capa de negocio |
| Legal | Interfaz en español; datos personales según la Ley 29733; producto simulado sin validez legal |
| Proyecto | Equipo de 3 integrantes; fase 1 el 12/11/2026 y sistema funcionando el 03/12/2026 |
| Integraciones | Servicios externos y pagos simulados |

### 1.2 Supuestos y dependencias

| ID | Supuesto o dependencia |
|---|---|
| SUP-01 | La municipalidad simulada tiene un procedimiento de licencia con dos variantes (indeterminada y temporal) y catálogos de giros, zonas y requisitos cargados como semilla |
| SUP-02 | La zonificación se obtiene de una matriz de compatibilidad de referencia, no de un catastro real |
| SUP-03 | Las notificaciones son correos simulados (se guardan en MongoDB y, en desarrollo, se ven en MailHog) |
| SUP-04 | Los usuarios usan un navegador moderno; los funcionarios trabajan con conexión estable |
| SUP-05 | Si cambia la norma, basta con actualizar parámetros, umbrales y requisitos (RNF-15), sin cambiar el código |

| Tipo | Descripción |

## 2. Requerimientos no funcionales

Cada requerimiento indica **cómo se verifica**, para que pueda probarse en la fase 2.

| ID | Categoría | Requerimiento | Verificación |
|---|---|---|---|
| RNF-01 | Seguridad: autenticación y acceso | Autenticación con JWT (access token de 30 min y refresh token de 8 h); contraseñas con bcrypt (costo ≥ 12); control de acceso por rol en cada endpoint (RBAC) | Pruebas de integración: endpoint sin token → 401; rol incorrecto → 403 |
| RNF-02 | Seguridad: comunicación y entradas | Todo el tráfico externo pasa por Nginx con HTTPS (certificado autofirmado en local). Validación de entradas con esquemas (Pydantic), consultas parametrizadas con el ORM, cabeceras de seguridad (CSP, HSTS, X-Frame-Options) y rate limit de 10 req/s por IP en `/auth` | Escaneo con OWASP ZAP baseline; pruebas negativas con inyección SQL y XSS |
| RNF-03 | Protección de datos personales | Cumplir la Ley N.° 29733: mínimo privilegio; en consultas públicas el DNI/RUC aparece enmascarado (`4567****`); no se registran contraseñas ni tokens en los logs | Revisión de código + prueba de la consulta pública |
| RNF-04 | Auditoría y trazabilidad | El 100 % de los cambios de estado y acciones sobre expedientes queda en bitácora (MongoDB) sin opción de editar ni borrar desde la aplicación | Prueba de integración: cada transición genera exactamente un evento |
| RNF-05 | Rendimiento | P95 < 2 s en consultas y bandejas con 100 usuarios concurrentes y 10 000 expedientes; carga de un archivo de 10 MB en < 5 s en red local | Prueba de carga con Locust/k6 (fase 2) |
| RNF-06 | Disponibilidad | 99 % en horario laboral (lunes a viernes de 8:00 a 18:00). Contenedores con `restart: unless-stopped` y health checks | Health check `GET /api/health` en Compose |
| RNF-07 | Mantenibilidad | Arquitectura en capas con dependencias en una sola dirección; lint (ruff) y tipos (mypy) sin errores; complejidad ciclomática ≤ 10 por función; código y API documentados (docstrings + OpenAPI) | Pipeline CI |
| RNF-08 | Testabilidad | Cobertura de ramas ≥ 70 % en la capa de negocio; integraciones externas detrás de interfaces (puertos) para usar dobles de prueba | `pytest --cov --cov-branch --cov-fail-under=70` en CI |
| RNF-09 | Usabilidad | Interfaz en español, responsiva (desde 360 px de ancho), validación de formularios en línea, mensajes de error comprensibles; un ciudadano presenta un expediente en ≤ 10 minutos con sus documentos a la mano | Prueba de usabilidad con 3 usuarios |
| RNF-10 | Accesibilidad | Nivel WCAG 2.1 AA en las pantallas públicas (contraste, etiquetas, navegación con teclado) | Lighthouse ≥ 90 en accesibilidad |
| RNF-11 | Observabilidad | Logs estructurados en JSON con `correlation_id` por petición; métricas en `/api/metrics` (formato Prometheus: peticiones, latencia, errores); errores 5xx registrados con stack trace | Revisión de logs en CI y local |
| RNF-12 | Integridad de datos | Transacciones ACID para cada transición de estado; hash SHA-256 de cada archivo verificado al descargar | Prueba de integración: archivo alterado → error de integridad |
| RNF-13 | Portabilidad y despliegue | Todo el sistema se levanta con `docker compose up -d` en Linux, Windows o macOS con Docker 24+; configuración por variables de entorno (`.env`) | Guía de despliegue probada en una máquina limpia |
| RNF-14 | Escalabilidad | API sin estado (la sesión vive en el JWT), por lo que se puede replicar detrás de Nginx | Levantar 2 réplicas del API en Compose |
| RNF-15 | Configurabilidad normativa | Plazos, umbrales de riesgo, requisitos, feriados y matriz de compatibilidad se parametrizan en BD sin tocar código | Cambiar un plazo en catálogo y ver el efecto |
| RNF-16 | Calidad del proceso | Repositorio en GitHub con ramas por funcionalidad, pull requests revisados por otro integrante, Conventional Commits, CI en cada push/PR y tags SemVer por incremento | Historial del repositorio |
| RNF-17 | Respaldo y recuperación | Script de respaldo diario (`pg_dump`, `mongodump`, copia del bucket) y procedimiento de restauración documentado; RPO 24 h, RTO 4 h | Guía de despliegue y operaciones |
| RNF-18 | Legalidad del producto simulado | Toda licencia y resolución generada lleva la marca de agua "DOCUMENTO SIMULADO – SIN VALOR LEGAL" | Inspección del PDF |
